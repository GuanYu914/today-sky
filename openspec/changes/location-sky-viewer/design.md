## 背景

本設計引入一個全新的 web 平台，用於查看不同地點的即時天空狀態。此專案旨在服務喜愛天空的使用者，讓他們能夠體驗來自各個地方的天空視覺之美，無論是為了放鬆、靈感或融入日常生活。

目前狀態：此專案沒有既有程式碼基礎。這是一個全新的實作。

限制條件：

- 必須能夠可靠地處理即時或接近即時的天空資料
- 使用者體驗應該簡單且注重視覺效果
- 應該可以從標準的 web 瀏覽器存取
- 考慮天氣/天空資料 API 的免費方案限制
- **安全性：所有 API keys 和敏感環境變數必須儲存在後端，絕不可暴露在前端代碼中**
- 程式碼必須通過 linting 和格式化檢查
- 測試覆蓋率需達到 80% 以上
- 所有功能需有端對端測試確保使用者流程正常運作

## 目標 / 非目標

**目標：**

- 建立視覺吸引人、響應式的 web 介面供天空觀賞
- 實作可靠的地點搜尋和選擇功能
- 取得並顯示準確的即時天空狀態（天氣、雲層、時間光線）
- 啟用具自動更新的桌布/背景模式
- 確保良好效能以快速視覺化天空
- 建立高品質、可維護的程式碼庫（完整的測試覆蓋、一致的程式碼風格）
- 自動化品質檢查流程（CI/CD 整合）

**非目標：**

- 天氣預報或歷史資料分析
- 社交功能（分享、留言、使用者個人檔案）
- Mobile 原生應用程式（以 web 優先）
- 初始版本的使用者認證系統（如果需要儲存偏好設定可之後新增）
- 即時影片或動畫天空模擬

## 決策

### 架構：Client-Side Rendering (SPA)

**決策：** 使用現代 JavaScript 框架（React、Vue 或 Svelte）建構 single-page application (SPA)，採用 client-side rendering。

**理由：**

- 天空資料更新需要動態呈現，無需重新載入頁面
- 桌布模式需要平滑、不中斷的更新
- Client-side rendering 為地點選擇和天空觀看提供更好的互動性
- 可以部署為靜態網站，透過 API 呼叫外部服務

**考慮過的替代方案：**

- Server-side rendering (SSR)：增加複雜度和主機需求，對此使用情境沒有顯著的 SEO 優勢
- 純靜態網站：不足以處理即時資料更新

### 資料來源：Weather API + 天文資料

**決策：** 使用 OpenWeatherMap API（或類似服務）取得即時天氣狀況，結合太陽位置計算函式庫以呈現準確的天空樣貌。

**理由：**

- OpenWeatherMap 提供即時天氣、雲量和基本狀況
- 免費方案支援初始發布的合理使用量
- 太陽/月亮位置演算法可以決定時間光線（黎明、白天、黃昏、夜晚）
- 結合兩者可提供寫實的天空呈現

**考慮過的替代方案：**

- Webcam/衛星影像：地點覆蓋有限、隱私疑慮、較高頻寬
- 純天文計算：缺少天氣/雲層資料
- 付費 weather API：初始版本成本過高

### 地點服務：Geocoding API

**決策：** 使用 OpenStreetMap Nominatim API 或類似的免費 geocoding 服務進行地點搜尋。

**理由：**

- 免費且開源
- 對於城市/區域層級的搜尋具有足夠的準確度
- 基本使用不需要 API key

**考慮過的替代方案：**

- Google Maps Geocoding API：需要 API key 和計費設定
- 基於 IP 的地理定位：不準確，不允許地點選擇

### 天空視覺化：CSS Gradients + Canvas

**決策：** 使用 CSS gradients 根據天氣和時間呈現平滑的色彩轉換，並可選擇使用 canvas 來疊加雲層。

**理由：**

- 效能好且輕量
- CSS gradients 提供平滑的天空色彩轉換
- Canvas 允許動態雲層渲染（如果需要）
- 不需要大型圖片資源

**考慮過的替代方案：**

- 預渲染圖片：變化有限、資源大小大
- WebGL 3D 渲染：對此使用情境過於複雜
- 影片背景：高頻寬、客製化有限

### 狀態管理：LocalStorage + Context

**決策：** 使用瀏覽器 LocalStorage 來持久化使用者偏好設定（儲存的地點），並使用 React Context（或同等機制）進行狀態管理。

**理由：**

- 基本偏好設定儲存不需要後端
- 簡單且足夠初始版本使用
- 如果之後需要，容易遷移到後端儲存

**考慮過的替代方案：**

- 後端資料庫：增加複雜度和主機成本
- Cookies：儲存容量較少、限制較多

### 開發工具與品質控制

**決策：** 建立完整的開發工具鏈，包含 ESLint、Prettier、單元測試（Vitest/Jest）和端對端測試（Playwright/Cypress）來確保程式碼品質。

**理由：**

- **ESLint**：自動檢測程式碼問題和潛在錯誤，強制執行一致的編碼風格
- **Prettier**：自動格式化程式碼，確保團隊協作時的一致性，減少程式碼審查中的格式爭議
- **單元測試（Vitest/Jest）**：驗證個別元件和函式的正確性，提供快速的回饋循環
- **端對端測試（Playwright/Cypress）**：模擬真實使用者操作，確保完整功能流程運作正常
- 這些工具可整合到 CI/CD 流程中，在部署前自動執行檢查

**工具選擇：**

- **Linting**: ESLint + TypeScript ESLint（如使用 TypeScript）
- **格式化**: Prettier with ESLint 整合
- **單元測試**: Vitest（Vite 專案）或 Jest（React 專案）+ Testing Library
- **端對端測試**: Playwright（跨瀏覽器支援佳、速度快）
- **測試覆蓋率**: 內建的 coverage 工具，目標至少 80% 覆蓋率
- **Pre-commit hooks**: Husky + lint-staged 確保提交前程式碼符合標準

**測試策略：**

- 單元測試重點：天氣資料處理、時間計算、色彩生成邏輯
- 端對端測試情境：地點搜尋流程、最愛管理、桌布模式切換、API 失敗處理

**考慮過的替代方案：**

- 不使用測試工具：風險過高，容易引入回歸錯誤，重構困難
- 僅使用 linting：不足以確保功能正確性
- 僅使用端對端測試：執行緩慢、維護成本高、回饋循環長

### 部署平台：Netlify

**決策：** 使用 Netlify 作為主要部署平台。

**理由：**

- **自動化部署**：與 Git 整合，推送程式碼後自動部署
- **環境變數管理**：簡單的介面設定 API keys 等敏感資訊
- **免費方案充足**：免費方案提供足夠的頻寬和建置時間供初期使用
- **自訂網域支援**：容易設定自訂網域和 HTTPS
- **預覽部署**：每個 Pull Request 自動建立預覽環境
- **邊緣函式**：未來如需要輕量後端可使用 Netlify Functions
- **建置快速**：針對靜態網站優化的建置流程

**設定需求：**

- `netlify.toml` 設定檔定義建置命令和發布目錄
- 環境變數透過 Netlify UI 或 CLI 設定
- 建置命令包含測試和 linting 檢查

**考慮過的替代方案：**

- Vercel：功能類似但在 Next.js 以外的框架支援上 Netlify 更靈活
- GitHub Pages：免費但功能較少（無環境變數、無預覽部署、無邊緣函式）
- Cloudflare Pages：功能強大但對初學者較不友善

### API 安全架構：Netlify Functions 代理層

**決策：** 使用 Netlify Functions（serverless functions）作為 API 代理層，所有第三方 API 調用都透過後端函式進行，API keys 絕不暴露在前端代碼中。

**理由：**

- **安全性**：API keys 儲存在 Netlify 環境變數（後端），前端代碼完全不包含敏感資訊
- **防止濫用**：使用者無法直接取得 API keys，無法繞過應用程式直接調用 API
- **速率控制**：可在 Functions 層實作額外的速率限制和快取邏輯
- **統一錯誤處理**：集中處理 API 錯誤和回應格式化
- **未來擴展性**：容易添加資料轉換、日誌記錄、監控等功能

**架構流程：**

```
前端 (SPA)
    ↓ fetch()
Netlify Functions (/.netlify/functions/)
    ├─ /weather → 調用 OpenWeatherMap API
    ├─ /geocoding → 調用 Nominatim API
    └─ /sun-position → 天文計算（或調用相關 API）
    ↓ 使用環境變數中的 API keys
第三方 API 服務
```

**實作需求：**

- 在 `netlify/functions/` 目錄建立 serverless functions
- Functions 使用 `process.env.API_KEY` 讀取環境變數
- 前端調用 `/.netlify/functions/weather` 而非直接調用第三方 API
- Functions 實作基本的錯誤處理和回應格式化
- （可選）在 Functions 層實作快取減少 API 調用

**考慮過的替代方案：**

- 直接在前端使用 API keys：嚴重安全風險，API keys 會暴露在客戶端代碼中
- 建立完整的後端服務器（Node.js/Express）：過於複雜，增加維護成本和主機費用
- 使用 API key 的 referrer 限制：不夠安全，仍可被繞過

## 風險 / 權衡

**[風險]** API keys 不慎暴露在前端代碼中 → **緩解措施：** 使用 Netlify Functions 作為代理層，所有 API keys 僅存在於後端環境變數；在代碼審查和 CI/CD 中加入檢查，確保沒有硬編碼的敏感資訊

**[風險]** Weather API 速率限制或服務停機 → **緩解措施：** 在 Netlify Functions 層實作快取、速率限制、顯示快取/備援天空狀態、提供清楚的錯誤訊息

**[風險]** 地點搜尋回傳模糊結果 → **緩解措施：** 顯示多個符合項目並附帶國家/區域詳細資訊，允許使用者精煉搜尋

**[風險]** 天空呈現可能無法完美符合真實狀況 → **緩解措施：** 設定使用者預期這是「詮釋性」視圖，而非即時攝影；著重藝術呈現

**[權衡]** 使用免費方案 API 限制請求量 → 接受此限制作為 MVP；如果使用量增長可以升級或新增多個 API keys

**[權衡]** 僅有 client-side 意味著沒有 server-side 快取天氣資料 → 架構較簡單但每個使用者都要自行抓取資料；初始規模可接受

**[權衡]** 完整的測試和品質工具增加初期設定時間 → 長期來看可大幅減少除錯時間、提升程式碼可維護性、降低回歸錯誤風險
